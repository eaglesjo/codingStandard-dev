# AI Engineering Standard 2.0 Final Gap Matrix

## Purpose

This document records the repository-grounded gap analysis for the final 2.0 hardening scope. The matrix is the durable basis for deciding what must be implemented before the 2.0 release candidate is frozen.

## Decision boundary

The 2.0 final scope contains four areas:

1. AI Code Quality & Verification
2. AI/LLM Evaluation
3. Development Observability & Provenance
4. Data/Model Reproducibility

Multi-agent AI model/provider mapping is explicitly deferred to the next version (`MODEL-ROUTING`). It must not be introduced as a 2.0 implementation dependency.

## Repository-grounded matrix

| Area | Current state | Evidence in repository | 2.0 decision |
|---|---|---|---|
| AI Code Quality & Verification | **PARTIAL** | `scripts/validation/validate.py` and the architecture/agent validation scripts provide executable validation gates; `code-review` and `testing-validation` Skills provide process guidance. No dedicated AI-generated-code quality contract or acceptance model was found in the inspected tree. | **Implement a focused quality/verification contract and executable checks**, without inventing a large new static-analysis framework. | 
| AI/LLM Evaluation | **MISSING / PARTIAL FOUNDATION** | Existing validation is primarily repository/runtime conformance and multi-agent contract validation. No dedicated LLM evaluation contract, evaluation case schema, scorer policy, or evaluation gate was found in the inspected tree. | **Implement a minimal vendor-neutral evaluation contract + fixtures + deterministic validation path.** | 
| Development Observability & Provenance | **IMPLEMENTED FOUNDATION / PARTIAL** | `core/validation/conformance-evidence.schema.json` defines runtime evidence, observations, checks, repository revision, runtime identity, and timestamps. `core/validation/evidence-provenance-policy.md` defines trust levels, promotion rules, and immutable evidence requirements. | **Harden the existing foundation**, especially traceability across development actions and acceptance, rather than creating a second provenance system. | 
| Data/Model Reproducibility | **PARTIAL** | `core/common/experiment.py` records standard version, experiment ID, variant, seed, config hash/config, model revision, dataset revision, environment profile, runtime config, and Git state. | **Complete reproducibility integrity/validation**, including explicit artifact identity and deterministic acceptance rules where justified. | 

## Important observations

### 1. Provenance is not a blank slate

The repository already has a meaningful evidence/provenance architecture. Runtime evidence is required to carry repository revision, runtime identity, scenario information, observations, and check-level results. The provenance policy also distinguishes structurally valid evidence from trusted/verified evidence. Therefore the final hardening work should extend and validate this system rather than duplicate it.

### 2. Experiment reproducibility is also not a blank slate

The shared experiment helper already captures model and dataset revision fields and a deterministic configuration hash, together with Git revision/dirty state. The remaining gap is turning these metadata fields into enforceable reproducibility guarantees rather than treating metadata emission alone as sufficient.

### 3. AI/LLM evaluation is the largest functional gap

The current validation system can establish conformance of the engineering system, but that is different from evaluating an AI/LLM behavior against a task-specific acceptance criterion. 2.0 needs a small, vendor-neutral evaluation layer that can express cases, expected evaluation dimensions, scoring, and acceptance without binding to a model provider.

### 4. AI code quality should remain engineering-quality focused

The goal is not to claim that AI-generated code is correct merely because it passes a single check. The 2.0 contract should connect generated-code changes to focused tests, broader validation, review evidence, and explicit acceptance. It should remain compatible with different languages and toolchains.

## Evidence-driven acceptance model

The four areas follow one common principle:

```text
Claim
  ↓
Evidence
  ↓
Validation
  ↓
Reproducibility
  ↓
Acceptance
```

The following distinctions are normative for 2.0:

- AI-generated code ≠ verified code
- a test existing ≠ the behavior being verified
- execution occurring ≠ execution succeeding
- a result existing ≠ the result being reproducible
- structurally valid evidence ≠ trusted evidence

## Implementation order

Use the smallest dependency chain:

```text
1. AI Code Quality & Verification
        ↓
2. AI/LLM Evaluation
        ↓
3. Observability & Provenance hardening
        ↓
4. Data/Model Reproducibility hardening
        ↓
5. Cross-area acceptance validation
        ↓
6. Full 2.0 CI + public-candidate audit
```

Parallel read-only analysis is allowed, but overlapping implementation writes must remain single-owner. Candidate revision must be frozen before independent validation.

## Out of scope for 2.0

The following remain deferred:

- provider/model adapters
- per-agent model assignment
- model routing policies
- provider fallback selection
- model/provider-specific provenance implementation

These belong to `MODEL-ROUTING` in the next version.
